# Phase 1 — RAG Document Ingestion & Vector Storage

## Overview

Phase 1 implements the **document ingestion pipeline** for the AWS RAG application.

The objective is to take documents stored in **Amazon S3**, process and split them into smaller chunks, generate vector embeddings using **Amazon Bedrock**, and store both the text and embeddings in **Amazon RDS PostgreSQL with pgvector**.

### Phase 1 Flow

```text
                Amazon S3
                   │
                   │ PDF
                   ▼
          ┌─────────────────┐
          │ PDF Processing  │
          │ Text Extraction │
          └────────┬────────┘
                   │
                   ▼
          ┌─────────────────┐
          │    Chunking     │
          │                 │
          │ 52 chunks       │
          └────────┬────────┘
                   │
                   ▼
          ┌─────────────────┐
          │ Embedding Model │
          │ Amazon Titan    │
          │ Embeddings      │
          └────────┬────────┘
                   │
                   │ 1024-dimensional vectors
                   ▼
        ┌───────────────────────┐
        │ Amazon RDS PostgreSQL │
        │                       │
        │      pgvector         │
        └───────────┬───────────┘
                    │
                    ▼
             document_chunks
```

# Components

## 1. Amazon S3

S3 is used as the document storage layer.

Example:

```text
Bucket:
rag-documents-prod

Document:
transformer.pdf
```

Documents uploaded to S3 become the input for the ingestion pipeline.

---

## 2. PDF Processing

The ingestion service downloads the PDF from S3 and extracts its text.

The PDF used for testing:

```text
Attention Is All You Need
```

The document contains approximately 15 pages.

The extracted text is then passed to the chunking component.

---

## 3. Chunking

Large documents cannot efficiently be passed directly to an LLM.

Therefore, the extracted document text is divided into smaller pieces called **chunks**.

The Phase 1 implementation uses configurable chunking parameters.

Example:

```python
chunk_size = 1000
overlap = 200
```

The overlap helps preserve context between neighboring chunks.

For the test document:

```text
PDF pages:       15
Total chunks:    52
```

Each chunk is assigned a unique `chunk_id`.

Example:

```text
chunk-0
chunk-1
chunk-2
...
chunk-51
```

---

# 4. Embeddings

After chunking, every chunk is converted into a numerical vector using **Amazon Bedrock Titan Embeddings**.

Conceptually:

```text
Text Chunk
    │
    ▼
Titan Embedding Model
    │
    ▼
[0.0123, 0.4532, 0.7821, ...]
```

The embedding dimension used in this project is:

```text
1024
```

Each chunk therefore has a corresponding 1024-dimensional vector representation.

Embeddings allow the application to perform **semantic similarity search** instead of relying only on keyword matching.

---

# 5. Amazon RDS PostgreSQL

Amazon RDS PostgreSQL is used as the persistent vector database.

Database:

```text
ragdb
```

Table:

```text
document_chunks
```

The table stores:

* Document ID
* Chunk ID
* Chunk content
* Embedding vector
* Additional document metadata

Example schema:

```sql
CREATE TABLE document_chunks (
    id BIGSERIAL PRIMARY KEY,
    document_id TEXT,
    chunk_id TEXT,
    content TEXT NOT NULL,
    embedding VECTOR(1024),
    source TEXT,
    page_number INT
);
```

---

# 6. pgvector

The PostgreSQL **pgvector** extension is used to store and search vector embeddings.

The extension was enabled in the RDS PostgreSQL database.

Example:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

The embedding column uses:

```sql
VECTOR(1024)
```

This allows PostgreSQL to store the embeddings generated by Titan.

---

# 7. Vector Index

An HNSW index is created for efficient similarity search.

Example:

```sql
CREATE INDEX document_chunks_embedding_idx
ON document_chunks
USING hnsw (embedding vector_cosine_ops);
```

The index uses **cosine similarity** for comparing embeddings.

This will be used in the retrieval phase to find chunks that are semantically closest to a user's question.

# End-to-End Ingestion Flow

The complete Phase 1 process is:

```text
1. Document uploaded to S3
             │
             ▼
2. Application downloads PDF
             │
             ▼
3. PDF text is extracted
             │
             ▼
4. Text is split into chunks
             │
             ▼
5. Each chunk is sent to
   Amazon Titan Embeddings
             │
             ▼
6. 1024-dimensional embedding
   is generated
             │
             ▼
7. Chunk + embedding + metadata
   are inserted into PostgreSQL
             │
             ▼
8. pgvector stores the embedding
             │
             ▼
9. HNSW index enables
   similarity search
```
